# プロトコル

Nostr-Rating のクライアントとスナップショット生成が、同じイベントから同じ結果を出すための決まりです。
別の実装を作るときや、レート計算に関わる変更を提案するときに参照してください。

- ルールの値（ステージ、締め切り、Glicko-2 の値、連戦の重み、シーズンなど）は [`configs/smash_sp.json`](../configs/smash_sp.json) を正とし、この文書には書きません。
- レート計算を変える変更は、すべてのクライアントとスナップショットの結果を変えます。シーズンの区切りで入れてください。
- 設計判断の理由は [`docs/adr/`](adr/) にあります。

以下、`<game>` は定義ファイルの `id`（`smash_sp`）です。

## イベント

独自の kind のイベントには必ず `["t", "nostr-rating"]` と `["game", "<game>"]` を付けます。content は JSON です。

| 用途 | kind | タグ | content |
|---|---|---|---|
| プロフィール | 0 | | `name` を表示名に使う。ほかの項目は残す |
| SNS の紐づけ | 10011（NIP-39） | `["i", "<platform>:<identity>", "<proof>"]` | 空 |
| 対戦設定 | 30078 | `["d", "nostr-rating:<game>:settings"]` | `stageBans`、`rangeChoice`、`rematchHours` |
| 募集 | 31751 | `["d", "<game>"]`、`["expiration", "<秒>"]`（NIP-40） | `firstFighter`、`rating`、`rangeChoice`、`rematchHours`、`settingsId`、`waitingSince`、`status`（`open` / `closed`） |
| 申し込み | 3751 | `["a", "31751:<募集者>:<game>"]`、`["p", "<募集者>"]` | `firstFighter`、`settingsId`、`rangeChoice`、`rematchHours`、`waitingSince` |
| マッチ成立 | 3752 | `["e", "<申し込みの id>"]`、`["p", "<p1>"]`、`["p", "<p2>"]` | `p1`、`p2`、`p1Fighter`、`p2Fighter`、`p1SettingsId`、`p2SettingsId` |
| 結果報告 | 3754 | `["e", "<マッチの id>"]`、`["p", "<相手>"]` | `result`（`win` / `lose` / `cancel`） |
| 部屋 ID・連絡 | 1059（NIP-17） | `["p", "<宛先>"]` | 下の「対戦ルームの連絡」 |

kind 3753 は鍵の引き継ぎ用に予約しています。

- マッチ成立は p1（募集した側）が署名します。content の `p1` は署名者と同じでなければなりません。
- 結果報告は置き換えのない通常のイベントです。送り直すたびに新しいイベントを出し、前の報告も残ります。
- 署名の正しくないイベントと、形の合わないイベントは無視します。重複は署名を確かめたあとに id で除きます。

### SNS の紐づけ

検証用の文は NIP-39 のとおり `Verifying that I control the following Nostr public key: <npub>` です。

| platform | identity | proof | 自動検証 |
|---|---|---|---|
| `github` | ユーザー名 | Gist の id | Gist の所有者と本文を確かめる |
| `mastodon` | `<インスタンス>/@<ユーザー名>` | 投稿の id | 投稿の `account.acct` がユーザー名と一致し、`account.url` のホストがインスタンスと一致し、本文に検証用の文がある |
| `twitter` | ユーザー名 | 投稿の id | しない（リンクを表示するだけ） |

形式に合わない identity と proof を持つ主張は無視します。

### 対戦ルームの連絡

部屋 ID、パスワード、チャットは NIP-17（rumor は kind 14、seal は kind 13）で送ります。
rumor には `["p", "<相手>"]` と `["e", "<マッチの id>"]` を付け、content は次のどちらかです。

- `{"type": "room", "roomId": "…", "password": "…"}`（p1 からのものだけを受け付ける）
- `{"type": "chat", "text": "…"}`

送信者は自分宛てにも控えを包みます。受け取った側は、送信者がそのマッチの p1 か p2 であることを確かめます。

## 有効な対戦

マッチ成立のイベントは次をすべて満たすときだけ有効です。

- 参照する申し込みが存在し、p2 が署名している
- 申し込みの募集者が p1 である
- 申し込みの `firstFighter` と `settingsId` がマッチの `p2Fighter` と `p2SettingsId` に一致する
- マッチの `created_at` が申し込みの `created_at` 以上で、その差が `matching.applicationTimeoutSec` 以下である
- マッチの `created_at` がそのシーズンの開始以上で、締め切り（下の「結果の確定」）がそのシーズンの終わり以下である

1つの申し込みに有効なマッチが複数あるときは、id が最小のものだけを使います。

## 結果の確定

対戦の締め切りはマッチの `created_at` + `report.deadlineSec` です。

1. 当事者（p1 と p2）の報告のうち、`created_at` がマッチの作成時刻から締め切りまでのものを使います。
2. 報告を `(created_at, id)` の昇順に見て、噛み合う組が初めてそろった時点で確定します。噛み合う組とは「一方の `win` と他方の `lose`」、または「双方の `cancel`」です。組はその時点の最新の報告どうしではなく、それまでに出したすべての報告で判定します。
3. 締め切りまでに組がそろわなければ、各自の最新の報告で判定します。

| 締め切り時点 | 結果 | マナーの目安 |
|---|---|---|
| 勝ちと負けの組がそろった | 確定 | 数えない |
| 中止の組がそろった | 中止 | 双方の「中止」に +1 |
| 双方が報告したが組がない | 食い違い | 双方の「食い違い」に +1 |
| 片方だけが報告した | 未報告 | 報告しなかった側の「未報告」に +1 |
| どちらも報告しなかった | 未報告 | 数えない |

## レート計算

計算はスナップショットの状態に、イベントを加えて進めます。

- 締め切りが `(前回の cutoff, 今回の cutoff]` に入る有効な対戦を、マッチの `(created_at, id)` の昇順に1件ずつ評価します。各対戦は1回だけ評価します。
- 主張が1つ以上ある kind 10011 が一度でも見えた公開鍵を「紐づけあり」とし、以後は外しません。確定した対戦は、双方が紐づけありのときだけレートに入れます。
- 各対戦はその2人にとっての1つの rating period として Glicko-2 で更新します。時刻 t はマッチの `created_at` です。
  1. 前回の対戦からの経過 `floor((t - 前回の t) / rating.inactivityPeriodSec)` 期間分、RD を広げます（`rating.initialRd` で頭打ち）。
  2. 相手の更新前の値を使って、勝者と敗者を更新します。
  3. 同じ2人の、時刻の差が `rematchWeight.windowSec` 未満の確定済みの対戦の数を n とし、`weights[min(n, 末尾)]` の重み w で、rating・RD・volatility をそれぞれ `更新前 + w × (更新後 − 更新前)` にします。
- 値は計算のたびに小数第6位で丸めます。
- 確定しなかった対戦は上の表のとおりマナーの目安だけを加えます。

クライアントは締め切り前でもすでに確定した対戦を、暫定値として上乗せして表示してよいです。確定した結果は覆らないので、締め切り後の計算と一致します。

## シーズン

シーズンは `seasons` の起点（`firstStartsAt`）から、`months` か月ごとに区切ります。月は `utcOffsetMinutes` の時差での暦の月で数え、id は 1 から順に振ります。一覧ではないので、誰も更新しなくてもシーズンは続きます。

- 締め切りがシーズンの終わりを越える対戦は、どのシーズンでも数えません。クライアントは、シーズンの終わりまでの残りが `report.deadlineSec` より短いときは、新しい対戦を始めません。
- 新しいシーズンは全員が初期値から始まります。前のシーズンの成績は最終スナップショットのサマリー（`season_summaries`）に残ります。
- クライアントは、手元のスナップショットが前のシーズンのものなら、今のシーズンを初期値から始め、サマリーだけを引き継ぎます。

## スナップショット

`snapshots/season_<N>/<cutoff の JST の日付>.json` に置き、`snapshots/latest.json` がそのパスと sha256 を指します。

- JSON はキーを再帰的に昇順に並べ、2スペースで字下げし、末尾に改行を1つ付けます。誰が生成しても同じバイト列になります。
- 主な項目は次のとおりです。
  - `cutoff`: この時刻までに締め切りを迎えた対戦を処理済み
  - `previous`、`previous_sha256`: 前のスナップショット
  - `config_sha256`: レート計算に関わる設定値のハッシュ
  - `inputs.event_ids_sha256`: 使ったイベントの id を昇順に `\n` でつないだ文字列の sha256
  - `players`: 公開鍵ごとの状態
  - `recent_pairs`: 連戦の判定に使う、直近の確定済みの対戦
- 使ったイベントの id は同じ名前の `.ids.txt` に1行1つ置きます。対象は評価した対戦、その申し込み、使った報告、初めて紐づけありにした kind 10011（公開鍵ごとに `(created_at, id)` が最小のもの）です。
- `cutoff` は生成する時刻より前でなければなりません。シーズンの途中で `config_sha256` が変わるスナップショットは作りません。
- 前のスナップショットのシーズンが終わっていたら、まずそのシーズンの終わりまでを処理した最終スナップショット（`snapshots/season_<N>/final.json`、`kind` は `final`）だけを作ります。次のシーズンの最初のスナップショットは、その次の生成で作ります。レート計算に関わる設定は、この2つの間でだけ変えられます。
- `season_summaries` は、シーズン id ごとに、そのシーズンに対戦した公開鍵の最終レート・最高レート・対戦数・勝敗を持ち、以後のスナップショットに引き継ぎます。

## マッチング

マッチの条件は、双方のクライアントがそれぞれ判定します。マッチは双方が受け入れて初めて成立するので、レート計算では条件を確かめません。

- **レート差:** 双方の `rangeChoice` のうち狭いほう。`null`（制限なし）は`matching.unlimitedStart` から待機1分ごとに `matching.unlimitedExpandPerMinute` ずつ広がります。
- **連戦:** 双方の `rematchHours` のうち長いほうの時間内に対戦した相手とは組みません。
- **マナーの目安:** 回数の合計の差が `matching.mannersMaxDiff` を超える相手とは組みません。
- **紐づけ:** 主張のない相手とは組みません。

レートとマナーの回数は、相手の自己申告ではなく、各クライアントが手元で計算した値を使います。

手順は次のとおりです。

1. 条件に合う他人の募集があれば申し込み、`matching.applicationTimeoutSec` の間、マッチ成立を待ちます。
2. なければ自分の募集を出し、`matching.heartbeatSec` ごとに出し直します。最初に条件を満たした申し込みに、マッチ成立を出します。
3. 一度募集を出したあとは、自分より先に待っていた（`waitingSince` が小さい。同じなら公開鍵が小さい）相手にだけ申し込みます。互いに申し込み合うのを防ぐためです。
4. 申込者は自分の申し込みに応えた正当なマッチだけを受け取ります（上の「有効な対戦」の条件）。
