# 0013. 先後を双方の乱数で決める

- 状態: 採用（2026-11-04）
- 0010 の「先後はマッチ成立のイベントの id から決める」を置き換える。

## 背景

0010 では、マッチ成立のイベントの id の最後の16進数で先後を決めていた。id はイベントの中身のハッシュで、マッチ成立のイベントは募集した側（p1）が作る。p1 は出す前に id を計算できるので、`created_at` を1秒ずつ変えて作り直せば、平均2回で好きな側を取れる。改造したクライアントなら、相手に気づかれずにできる。

チェスでは1つ目の側が白なので、先手を選べることになる。スマブラSP でも、部屋を立てる側（P1）を選べる。

## 決定

先後を、募集した側と申し込んだ側がそれぞれ作った乱数を合わせて決める（コミット・リビール）。

1. 募集した側は32バイトの乱数 s<sub>1</sub> を作り、そのハッシュ SHA256(s<sub>1</sub>) を募集の `seedHash` に載せる。乱数そのものはまだ出さない。
2. 申し込んだ側は募集の `seedHash` を申し込みに写し、自分の32バイトの乱数 s<sub>2</sub> を申し込みの `seed` に載せる。
3. 募集した側はマッチ成立の `seed` に s<sub>1</sub> を明かす。
4. SHA256(s<sub>1</sub> ‖ s<sub>2</sub>) の最後の16進数が偶数なら p1、奇数なら p2 が1つ目の側。

マッチの `seed` のハッシュが申し込みの `seedHash` と合わない対戦は、有効な対戦にしない。

- 申し込んだ側は s<sub>1</sub> を知らずに s<sub>2</sub> を決めるので、先後を選べない。
- 募集した側は s<sub>2</sub> を見る前に s<sub>1</sub> を決めて、ハッシュを出している。あとから別の乱数を明かすと、ハッシュが合わず、対戦が無効になる。
- 1回の探索で明かすのは1回だけで、明かすと探索が終わる。次の探索では新しい乱数を作る。明かした乱数を使い回すと、次の申し込み側が先後を選べるためである。
- 申し込んだ側は、1回の探索の中で同じ `seedHash` に申し込み直すときは、前と同じ乱数を使う。新しい乱数にすると、募集した側は都合の悪い申し込みに応えずに待つだけで、申し込み直しのたびに先後を引き直せるためである。

### 検討した案

- **申し込みの id から決める:** 今度は申し込んだ側が `created_at` を変えて選べる。
- **双方の id を合わせる:** 後から出すほうが相手の id を見てから作り直せる。どちらか一方の id を後から作る限り、同じことが起きる。
- **第三者の乱数（公開の乱数ビーコンなど）:** 外部のサービスに頼ることになり、そのサービスがなくなると対戦できない。

## 影響

- 募集した側は、両方の乱数を知った時点で先後が分かる。都合が悪ければマッチ成立を出さずに、探索をやり直すことはできる。新しい `seedHash` の募集には、同じ相手がまた新しい乱数で申し込んでくることがあるので、やり直すたびに先後を引き直せる。そのたびに募集を出し直して相手の申し込みを待つ手間はかかるが、引き直しそのものは防げない。2人でコインを投げる方式では、後から結果を知る側のこの「やめる」を防ぐ方法がない。
- 募集・申し込み・マッチ成立のイベントの形が変わる。古い形のマッチ成立は `seed` がないので、有効な対戦にならない。利用者がまだ開発者だけなので、移行の仕組みは作らずに切り替える。
- 対戦ルームは申し込みを読んで確かめるまで先後を出さない。
