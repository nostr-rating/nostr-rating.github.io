# 0016. 署名アプリに任せた端末の署名には、掲載用の鍵の署名も要る

- 状態: 採用（2026-11-04）
- 0008 の「`icp` は載せた全端末、`ixn` は有効な端末1つが本文に署名する」と、証明書の署名に条件を足す。

## 背景

端末の鍵は、WebCrypto の P-256 の鍵か、NIP-07 の拡張や NIP-46 の署名アプリ（以下、署名アプリ）に任せた schnorr の鍵である。署名アプリの鍵は、ふつう利用者がほかの Nostr のサイトでも使う普段の鍵である。

schnorr の端末が KEL の本文や毎日の証明書に署名するときは、content に digest だけを入れた、タグのない kind 23753 のイベントに署名してもらう。この頼みは、ほかのサイトからも同じ形で出せる。

1. ほかのサイトが、リレーで公開されている aid と KEL の最新の番号から、攻撃者の端末を足して利用者の端末を取り消す `ixn` の本文を作る。
2. そのサイトは、本文の digest を content に入れた kind 23753 への署名を署名アプリに頼む。確認の画面に出るのは kind と64桁の16進数だけで、利用者は Nostr-Rating で毎日同じ承認をしている。
3. 承認されると、サイトは署名を KEL の形に詰め、自分の鍵で kind 3753 として出せる。`ixn` は有効な端末1つの署名で通り、kind 3753 を誰が出したかは確かめていないので、攻撃者の端末が足される。

証明書の digest への署名を取られた場合は、KEL に跡を残さずに最大1日なりすませる。復活の言葉で入れ替えれば戻せるが、それまでにスナップショットで確定した結果は残る。

## 決定

schnorr の端末が本文や証明書に署名するときは、その端末の登録にある掲載用の鍵（`publisher`）でも、同じ digest に同じ形で署名する。

- KEL の本文: `sigs` に、`signer` を掲載用の鍵にした署名を足す。掲載用の鍵の署名がない schnorr の端末の署名は数えない。
- 証明書: `publisherSig` に掲載用の鍵の署名を入れる。確かめる鍵は KEL に記録した掲載用の鍵で、証明書の `publisher` は使わない。
- 掲載用の鍵が端末の鍵と同じ登録は受け付けない。同じだと、署名アプリの署名がそのまま掲載用の鍵の署名になる。
- P-256 の端末には要らない。P-256 の鍵はアプリの中にしかなく、ほかのサイトからは使えない。

掲載用の鍵はアプリが端末ごとに作り、nostr-rating.github.io の保存領域に置いている。ほかのサイトが署名アプリから署名をいくら引き出しても、掲載用の鍵の署名がないので、KEL のイベントも証明書も作れない。

### 検討した案

- **kind 3753 のイベントを出した鍵を確かめる:** KEL の本文を載せたイベントの署名者が、署名した端末の掲載用の鍵であることを必須にする。スナップショットは本文と署名だけを記録していて、イベントの署名者を持っていないので、記録の形も変える必要がある。証明書には使えない。
- **署名を頼む中身を読める文にする:** content を「Nostr-Rating: 端末の追加」のような文にする。利用者が読まないと効かず、content を出さない署名アプリもあるので、これだけでは防げない。

## 影響

- ほかのサイトに署名アプリの署名を取られても、端末を足されたり、取り消されたり、なりすまされたりしない。
- 配信される JavaScript がすり替えられた場合は、両方の鍵を使われる。これは今の既知の限界と同じである。
- schnorr の端末の KEL のイベントと証明書は、署名1つ分（約250バイト）大きくなる。証明書はアプリのイベントごとにタグで持ち歩く。
- これまでの schnorr の端末の KEL と証明書は通らなくなる。公開しているスナップショットのアカウントはどちらも P-256 の端末なので、移行の仕組みは作らずに切り替える。
