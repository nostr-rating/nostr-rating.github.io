# 0011. 人数と対戦が増えても、集計と同期が回るようにする

- 状態: 採用（2026-10-29）

## 背景

今の作りは、人数が増えると集計とクライアントの同期が回らなくなる。開発環境のローカルリレー（選手112人、イベント711件）で測った結果は次のとおりである。

- ブラウザの同期1回に17〜26秒かかった。
- Node で同期の処理だけを測ると15.7秒で、うち約8.5秒が署名の検証のやり直し、約7秒がアカウントごとの問い合わせだった。
- 1回の同期の中で KEL の一覧を8回ほど組み立て直し、そのたびに全員分の署名を確かめている。異なる340件の KEL の署名を、1,376回検証していた。
- イベントの署名は異なる721件を1,602回検証していた。問い合わせごとに別のオブジェクトとして届くので、検証済みの記録（WeakMap）が効かない。
- 問い合わせは1件ずつ順番に投げていて、257回だった。
- KEL の一覧の組み立ては、1アカウントあたり約13ミリ秒かかる（Node で300アカウント。半数は入れ替えを1回含む）。

コードを読んで分かったことは次の3つである。

- クライアントは同期のたびに、`latest.json` とスナップショット全体を取り直している。
- 画面を開くと同期が同時に3本走ることがある。先に始めた同期が遅れて終わると、古い結果で表示を上書きする。
- `Resolver` は、知らないアカウントが1人見つかるたびに、全員分の KEL の一覧を組み立て直す。

スナップショットの大きさは1アカウントあたり約3KB だった。内訳は KEL が約2KB、`players` が約430B、`accounts` が約390B、シーズンのサマリー1つが約230B である。`kels` と `accounts` はシーズンをまたいで引き継ぎ、対戦しなかったアカウントの分も残る。そのため、ファイルの大きさを決めるのは、そのシーズンの選手の数ではなく、これまでに作られたアカウントの累計である。約3万アカウントで、GitHub の1ファイルの上限（100MB）に届く。

1シーズンの選手は1万〜2万人を見込む。参加者が入れ替わり続けると、累計は数シーズンで3万を超える。チェスのように遊ぶ人の多いゲームでは、少しだけ遊んだアカウントが大量に残り、累計の見積もりは難しい。

リポジトリの大きさは、今のところ問題にならない。1000アカウント分（約2.9MB）の全量を、毎日1割の選手と2%の KEL を変えて60日分コミットする模擬データで試した。`git gc` で圧縮すると、`.git` は40MB から約1MB になった。

目標は、累計で2万〜10万アカウントとする。スナップショットの生成は数分以内、クライアントの同期は数秒以内に収める。累計に上限の見えないゲームでも、ファイルの大きさが上限に当たらない形にする。クライアントが読む量も、累計ではなく、そのシーズンの選手の数と、新しいイベントに出てくるアカウントの数で決まるようにする。

## 決定

### KEL の署名は、確かめる回数を減らす

- スナップショットの生成は記録済みの KEL も含めて、1回の実行で全員分を1回だけ確かめる。
- クライアントは新しいイベントに出てきたアカウントの KEL だけを、スナップショットから読んで、使う時点で確かめる。ランキングの表示には KEL を使わない。
- 署名は P-256 を WebCrypto で、Nostr のイベントを nostr-wasm で確かめる。開発機（Intel Core i5-8600）で、1回あたりそれぞれ約0.15ミリ秒と約1ミリ秒だった。確かめ直しても負担が小さいので、確かめた結果はページを開いている間だけ覚え、端末には残さない。
- スナップショットに書かれた KEL を、確かめずに使うことはしない。偽の KEL を書き込まれると、他人の端末を足してなりすませるためである。

### 同じ署名は1回だけ確かめる

- 署名を確かめた結果を、上限のある表に覚える。キーは KEL の署名なら鍵・digest・署名、イベントなら id・pubkey・署名とする。
- スナップショットの生成では表の上限を外す。全員分を先に確かめてから使うので、古いものから捨てると、使う前に消えるためである。
- 結果はキーだけで決まるので、覚えても結果は変わらない。
- イベントは、id が中身から計算した値と合うことを毎回確かめる。

### KEL の一覧は、変わったアカウントの分だけ評価し直す

1回の取得の中と `Resolver` で、全員分を組み立て直さない。イベントが増えたアカウントだけを評価し直す。

### 問い合わせをまとめ、あふれたときだけ分ける

- 取り切る必要がある問い合わせは、複数のアカウントをまとめて投げる。`authors` に並べるのは、今までどおり100までとする。
- 1つの秒に1ページを超えるイベントがあって取り切れないときは、アカウントを半分に分けて投げ直す。1アカウントまで分けても取り切れないものだけを `excluded` にする。どのアカウントが `excluded` になるかは、今と変わらない。
- 同時に投げる問い合わせは、リレーごとに4本までとする。

### クライアントの同期を1本にする

- `latest.json` の sha256 が前回と同じなら、スナップショットを取り直さず、手元に読んだものを使う。
- 同期は同時に1本だけ走らせる。走っている間に頼まれた分は、終わったあとに1回だけやり直す。古い結果で表示を上書きしない。

### スナップショットを分け、中身をリポジトリの外に置く

0005 と 0009 のうち、スナップショットの全体を `snapshots/` に置く部分を、次のように置き換える。

- スナップショットは目次と部品に分ける。
  - 目次にはシーズン、`cutoff`、前回の目次とその sha256、設定のハッシュ、`excluded`、部品の一覧（sha256、大きさ、置いたリリース）、KEL の索引の sha256 と大きさを入れる。
  - リリースに置く部品は次の5種類である。
    - `players`: そのシーズンの選手の成績、`recent_pairs`、選手の公開情報（名前と紐づけ）、選手の KEL の部品の sha256。
    - `accounts`: 全アカウントの最新の公開情報。
    - `kels`: 全アカウントの KEL。
    - `accounts` と `kels` は、aid の先頭1文字ごとに16個に分ける。1つの部品が大きくなりすぎないようにするためで、1本の文字列のままだと約26万アカウントで Node の文字列の上限に当たる。変わっていない部品は前のリリースを指したままにする。
    - `ids`: その回に使ったイベントの id。
    - シーズンの部品: 終わったシーズンの成績と、その時点の選手の公開情報。前の目次にあれば作り直さずに使うので、それ以後変わらない。
  - 配信にだけ置く部品は `kels` の部品から作り直す。
    - KEL ごとの部品。
    - KEL の索引。aid の先頭2文字ごとの部品（aid → KEL の部品の sha256）と、その一覧である。
- リポジトリには目次と `latest.json` だけを置く。ハッシュのつながりは、これまでどおりリポジトリの履歴に残る。
- 部品は目次ごとのリリースに `<sha256>.json` の名前で置く。タグは目次のパスから決める（`snapshots/smash_sp/season_1/2026-10-02.json` なら `snapshot-smash_sp-season_1-2026-10-02`）。前の回と同じ部品は上げ直さず、目次はその部品を最初に置いたリリースを指す。
- 生成は前回の部品をリリースから取り、sha256 を確かめてから使う。新しい部品をリリースに上げてから、目次をコミットする。
- 配信は GitHub Pages で行い、スナップショットを積むたびに配信し直す。`snapshots/<game>/` の下に `latest.json` と目次を置く。`players`、シーズンの部品、KEL の索引、KEL ごとの部品は、全ゲームで共通の `snapshots/parts/<sha256>.json` に置く。同じ KEL を記録したゲームどうしでは1つにまとまる。KEL の索引は `kels` の部品から作り直し、目次の sha256 と合うことを確かめる。`accounts` と `ids` は配信しない。リレーの一覧（`configs/relays.json`）も同じ配信元に置く。
- クライアントは `latest.json`、目次、部品の sha256 を確かめてから使う。毎回読むのは目次と `players` とシーズンの部品だけである。KEL は新しいイベントに出てきたアカウントの分だけを読む。そのシーズンの選手なら `players` にある sha256 から、そうでなければ索引から引く。
- `latest.json` が無い（404）ときは、クライアントは今のシーズンの最初から計算する。fork した直後や、開発環境で動かすためである。
- クライアントは、スナップショットに公開情報がある選手について、スナップショットの時点より新しい公開情報だけをリレーに聞く。
- 独自のイベントに `["t", "nostr-rating:<game>"]` を付け、対戦はこのタグでゲームごとに問い合わせる。リレーは1文字のタグでしか絞り込めないためである。
- スナップショットの形式は `schema_version` 3 とする。公開前なので、今の `snapshots/` は消し、古い形式は読まない。

### 選ばなかった置き場所と分け方

- リリースの添付ファイルを、ブラウザから直接読むことはしない。ダウンロードの応答に CORS のヘッダーが付かないためである。
- Actions の成果物はログインしないと取れず、保存は最長90日なので使わない。
- Blossom（sha256 で引く Nostr のファイル置き場）は、今は使わない。
  - 仕様（BUD-01）では、どのサーバーも `Access-Control-Allow-Origin: *` を付けて `GET /<sha256>` で返すので、ブラウザから読める。
  - 一方、どれだけの期間残すか、どの大きさと種類を受け付けるか、料金を取るかはサーバーごとに決まる。
  - 公開サーバーの例では、無料で受け付けるのが画像・音声・動画だけのものや、60日読まれないと消すものがある。
  - 書き込みには Nostr の鍵による署名（kind 24242）が要るサーバーが多く、Actions に鍵を持たせる必要がある。
  - 部品は sha256 で確かめるので、置き場所を後から足しても仕組みは変わらない。自分でサーバーを立てる人が写しを置けるようにすることは、あとで考える。
- `accounts` と `kels` を aid の先頭で16個や256個に分けて、クライアントに配信する案は選ばなかった（リリースに置く部品を16個に分けるのは、生成の都合である）。1日に数百人が対戦すると、ほぼすべての部品に誰かが入る。KEL は毎日どこかが変わるので、前の日に読んだ部品も使えない。10万アカウントを256個に分けると、1部品は約780KB になる。新しいイベントに出てくるアカウントが100人なら約65MB、500人なら約170MB（圧縮前）を、その日の最初の同期で読む。1人1日65MB なら、Pages の配信量の目安（月100GB）に、毎日開く人が約50人で届く。
- 目次にすべての KEL の sha256 を並べる案も選ばなかった。10万アカウントで目次が約15MB になり、毎日変わる。

## 影響

- 偽の KEL をスナップショットに書き込まれても、次の生成とクライアントは署名から気づける。
- 取り切れないアカウントがあると、そのたびに問い合わせが増える。攻撃者1人あたり、まとめた問い合わせの数の対数程度である。
- クライアントが読む量は、そのシーズンの選手の数と、新しいイベントに出てくるアカウントの数で決まる。
  - `players` は選手1人あたり約700B（gzip で約170B）で、1シーズン1万2千人なら約8MB（gzip で約2MB）になる。これに `recent_pairs`（直近48時間の確定済みの対戦。1件約170B）が加わり、1日1万対戦なら約3.3MB 増える。中身が変わる毎日の最初の同期で読む。
  - KEL は1アカウントあたり約1〜2KB である。読むのは、前のスナップショットの `cutoff` から、締め切り（24時間）と使い捨ての鍵の期限（24時間）をさかのぼった時刻以降のイベントに出てくるアカウントである。毎日作るので、おおよそ直近2〜3日に動いたアカウントになる。
- 上限に届くのは、次のときである。
  - `kels` の部品を1つの文字列として読み書きするので、16個に分けた1つが Node の文字列の上限に当たる、累計およそ400万アカウントで生成が止まる。
  - Pages のサイト全体は1GB までで、KEL ごとの部品だけで、1つ2KB なら累計およそ50万アカウントで届く。選手ページと公開 API も、選手の累計に比例して増える。
- リリースは毎日ゲームの数だけ増える。リリースの一覧から探していたもの（復活の道具の入手先）は、タグから探す。
- 生成は毎日、記録済みの全アカウントの鍵ごとに KEL と証明書を問い合わせる。`#t` をあふれさせる攻撃を受けても、既知のアカウントの対戦を取りこぼさないためで、この仕組みはそのまま残す。累計10万アカウントなら、1ゲームあたりリレーごとに約2000回（見積もり）になる。
- 紐づけの確認の結果は、公開 API の `claims.json` に書き出し、次の配信で使い回す。7日より新しい結果は確かめ直さない。GitHub の API の回数の上限に当たらないようにするためである。
- スナップショットを積むたびに、Pages を配信し直す必要がある。fork して動かす人は Actions に加えてリリースと Pages を使える状態にしておく必要がある。
- `snapshotBase` で取得元を差し替える人は、配信と同じ並び（`npm run site` で書き出したもの）で置く必要がある。
- この ADR の決定はレートの結果を変えない。シーズンの区切りを待たずに入れられる。同じイベントから、スナップショットを使った同期と使わない同期で同じレートになることを、ローカルのリレーで確かめた。
