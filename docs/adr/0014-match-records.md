# 0014. 評価した対戦ごとの記録をスナップショットに残す

- 状態: 採用（2026-11-04）

## 背景

スナップショットは選手ごとの最新の状態（rating、RD、volatility など）と、使ったイベントの id の一覧を持つ。1つの対戦で値がどう変わったかを確かめるには、シーズンの最初から全部のイベントを集めて計算し直すしかない。古いイベントは公開リレーから消えていくので、時間がたつほど確かめにくくなる。

Elo のレートを Nostr のイベントで配る別の実装では、1対戦ごとに「対戦前の値・対戦後の値・スコア・K」を1つの記録にして、記録だけで更新を計算し直せるようにしている。本プロジェクトにも同じ考え方を取り入れる。

## 決定

- スナップショットの部品に `matches` を足す。その回に評価した対戦を評価した順に並べ、1件ごとに次を持つ。
  - マッチの id、作成時刻、p1、p2
  - 結果（`p1`・`p2` は勝った側、`draw`、`cancel`、`mismatch`、`no_report`）と、`no_report` のときに報告しなかった側
  - レートに入れた対戦だけ、連戦の重みと、双方の「対戦前の値・休んでいた期間の数・対戦後の値」
- 対戦前の値は休んでいた分の RD を広げる前の値にする。広げる手順も記録だけで計算し直せるようにするためである。
- 記録とゲームの定義だけから更新を計算し直す関数（`recomputeRating`）を core に置く。
- 部品はリリースに置くほか、GitHub Pages でも配る。クライアントは読まない。
- 目次の `schema_version` は 3 のままにする。足すのは部品1つだけで、この部品を作る前の目次は読める。

記録はレート計算の結果を書き出したものである。計算の決まりは変えない。

### 検討した案

- **記録を Nostr のイベントとして出し、生成する側の鍵で署名する:** 他の Nostr のツールから読みやすくなる。一方で、生成する鍵を信用する形になり、運営に頼らない方針と合わない。スナップショットの目次は sha256 でつながっていて誰でも作り直せるので、その中に置けば足りる。
- **Elo 用のイベントの形に合わせる:** その形は K を持つ Elo 向けで、Glicko-2 の RD と volatility を表せない。仕様もまだ草案である。

## 影響

- 1つの対戦は `matches` の部品の記録と定義だけで確かめられる。記録を選手ごとに並べると、前の対戦の対戦後の値が次の対戦の対戦前の値につながる。そのため、1人の成績を対戦ごとにたどって確かめられる。
- 連戦の重みは同じ2人の直近の記録と照らして確かめる。1件の記録だけでは確かめられない。
- 部品は対戦1件あたり約0.5KBで、毎日の対戦の数に比例して増える。
