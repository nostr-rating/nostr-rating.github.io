# Nostr-Rating

運営のいない、1対1の対戦ゲームのレート戦です。
対戦の募集、結果の報告、レートの計算を、中央サーバーなしで [Nostr](https://github.com/nostr-protocol/nips) の上で行います。

ゲームごとのルール（キャラ、ステージ、試合の形式、報告の締め切り、レートの値など）は、定義ファイル（`configs/<ゲーム>.json`）にまとめています。
今は大乱闘スマッシュブラザーズ SPECIAL（[`configs/smash_sp.json`](configs/smash_sp.json)）とチェス（[`configs/chess.json`](configs/chess.json)）の定義が入っていて、利用者はアプリの画面の上でゲームを選びます。

アプリは https://nostr-rating.github.io/ で開けます。

> **状態:** 開発中です。仕様や保存形式は予告なく変わることがあります。

Nostr-Rating は有志が作る非公式のソフトウェアです。対応しているゲームの開発元・販売元とは関係ありません。ゲームの名前は、それぞれの権利者の商標です。

## なぜ作ったか

スマブラSP 向けの非公式レート戦サイト「スマメイト」は、2026年10月25日に閉鎖されました。
運営がいなくなると、サービスは続けられません。

Nostr-Rating は次の2つの考え方で、運営に依存しないレート戦を作ります。

1. **情報を守ろうとしないことで、安全性を保証する。**
   守るべき個人情報も、秘密のデータベースも持ちません。対戦結果はすべて本人の署名付きで公開され、誰でも検証できます。
2. **運営がいなくても続く。**
   仕組みだけで回るので、特定の人やサーバーがいなくなっても止まりません。メンテナが入れ替わっても続けられるよう、コードと手順をすべて公開しています。

## 仕組み

```
 ┌────────────── ブラウザ（GitHub Pages から配信）──────────────┐
 │ Web アプリ（React）                                          │
 │   ・鍵: 端末の鍵（WebCrypto）と毎日の使い捨ての鍵            │
 │   ・手元のキャッシュ: SQLite（OPFS）                          │
 │   ・レート計算: packages/core（スナップショット + 差分）      │
 └──────────┬───────────────────────────────┬──────────────────┘
            │ WebSocket（複数リレーに同時接続） │ HTTPS
   ┌────────▼────────┐               ┌─────────▼───────────────────┐
   │ 公開 Nostr リレー │               │ GitHub                        │
   │（configs/relays.json）│          │  Pages: snapshots/<ゲーム>/  │
   └────────▲────────┘               │  リポジトリ: 目次と configs/  │
            │                         │  リリース: 部品               │
   ┌────────┴────────────────────────┐ └─────────▲───────────────────┘
   │ スナップショット生成（Actions で毎日）│──────────┘
   └─────────────────────────────────┘
 復活の道具（HTML 1ファイル）: リリースからダウンロードし、普段のアプリとは別の場所で開く
```

### データの流れ

1. **アカウント:** アカウントは1つの鍵ではなく、鍵の出来事の記録（KEL）で表します。端末の鍵は取り出せない形で端末にしまい、
   毎日の使い捨ての鍵に証明書を出します。端末を失くしたり盗まれたりしても、紙に書いた「復活の言葉」でアカウントを復元できます
   （[ADR 0008](docs/adr/0008-key-event-log.md)、利用者向けの説明はアプリの「ヘルプ」）。
2. **紐づけ:** アプリが「このアカウントは私のものです」という文を表示し、プレイヤーはそれを X に投稿するか GitHub の Gist に貼ります。
   どちらも自動で確認します。紐づけのないアカウントはレートの対象にならず、同じ X や GitHub のアカウントを紐づけたアカウントどうしは、
   選手の画面と公開 API で互いに表示します。1人で何個もアカウントを作っても、同じ SNS アカウントで紐づけていれば同じ人のものだと分かるようにするためです。
3. **募集と申し込み:** 「対戦相手を探す」を押すと、条件に合う募集に申し込むか、自分が募集を出します。
   条件はレート差・連戦・マナーの目安の3つで、どれも双方のクライアントがそれぞれ判定します。
4. **マッチ成立:** 募集した側が申し込み（申し込んだ側の署名付き）に応えるマッチイベントを出します。
   先後（スマブラSP の P1・P2、チェスの白・黒）は双方の乱数を合わせて決まり（[ADR 0013](docs/adr/0013-seat-draw.md)）、1つ目の側の人が部屋 ID と
   パスワード、または対局の招待リンクを、暗号化 DM（NIP-17 / NIP-44）で相手にだけ送ります。
5. **結果報告:** 双方が「勝ち／負け／中止」（引き分けのあるゲームでは「引き分け」も）を署名付きで報告します。噛み合う組がそろった時点で確定し、日時を遡らせた報告を後から足しても覆りません。勝ち・負け・引き分けを報告した人の中止は数えません。
6. **レート計算:** Glicko-2 で計算します。対戦は報告の締め切りを迎えた時点で1回だけ評価し、成立した時刻の順に処理します。
7. **スナップショット:** 全プレイヤーのレートをまとめたスナップショットを、GitHub Actions が毎日ゲームごとに作ります。目次は `snapshots/<ゲーム>/` に、中身の部品はリリースに置き、GitHub Pages から配ります（[ADR 0011](docs/adr/0011-scale.md)）。
   クライアントは最新のスナップショットのうち、そのシーズンの選手の部品と、新しいイベントに出てきたアカウントの KEL だけを読み、それ以降のイベントを足して計算します。選手ページと、ほかのサイト向けの公開 API（[docs/api.md](docs/api.md)）もここから作ります。

### 誰でも検証できる理由

- 対戦・申し込み・報告はすべて、本人の端末が証明書を出した使い捨ての鍵で署名した Nostr イベントです。第三者は作れず、書き換えると署名が合わなくなります。
- 計算は決定的です。同じイベントの集合からはどこで計算しても同じ結果になります（イベントの重複、届く順番、スナップショットの区切り方に左右されません）。
- スナップショットには計算に使ったイベント ID 一覧のハッシュ、前のスナップショットのハッシュ、設定値のハッシュが入っています。
- スナップショットには評価した対戦ごとの対戦前と対戦後の値も入っています。全体を計算し直さなくても、1つの対戦の増減を記録だけで確かめられます（[ADR 0014](docs/adr/0014-match-records.md)）。
- スナップショットとリレー一覧の取得元は、アプリの設定で差し替えられます。このリポジトリがなくなっても、フォークした先で同じように動きます。

GitHub の履歴は改ざんを「できなくする」ものではなく、「しても分かる」ようにするものとして使っています。

## 対戦ルール

アカウントは全ゲームで共通で、レート、対戦設定、ランキング、シーズンはゲームごとに分かれます。
ゲームを足すときは、定義ファイルを書いて [`configs/games.json`](configs/games.json) に足します。アプリもスナップショット生成もこの一覧にあるゲームをすべて扱います。
定義の形と、どこまでを定義で表せるかは [ADR 0010](docs/adr/0010-multiple-games.md) にあります。

### スマブラSP

スマブラSP のオンラインのレート戦で広く使われている形式に合わせています。ステージや締め切りなどの値はすべて [`configs/smash_sp.json`](configs/smash_sp.json) にあり、アプリの対戦ルームにも表示されます。

- 2本先取。部屋を立てるのは P1 の人で、部屋 ID とパスワードは対戦相手にだけ届く。P1 と P2 はマッチごとに偶然で決まる
- 部屋のパスワード: P1 の端末が対戦ごとに数字4桁を偶然で作る。送る前に4〜8桁の数字に書き換えられる。設定画面で固定の初期値を決めると、偶然で作る代わりにそれを使う（初期値はその端末にだけ保存し、公開しない）
- 1戦目: 双方の拒否ステージを除いたステージから各自が選び、ゲーム内の抽選に従う
- 2戦目以降: 直前の敗者が選び、勝者は「おまかせ」。除くのは、勝者が敗者のキャラに設定した拒否ステージだけ
- 拒否ステージ: 相手のキャラごとに設定する。拒否ステージを共有するキャラの組もある
- キャラ変更: 2戦目以降に変えられるのは直前の敗者だけ
- 結果報告には締め切りがある。「未報告」「中止」「食い違ったまま締め切り」の回数を「マナーの目安」として数え、シーズンごとにリセットする。回数の差が大きい相手とはマッチしない

### チェス

性質の違う2つ目のゲームとして入れています。値は [`configs/chess.json`](configs/chess.json) にあります。

- 1局で勝敗を決める。引き分けがある
- 持ち時間は15分＋1手ごとに10秒（国際チェス連盟の世界ラピッド選手権と同じ）
- 対局は、双方が使えるオンラインの対局サービスで行う。白の人が招待リンクを作って送り、黒の人はリンク先のホスト名を確かめてから開く。どのサービスを使うかはアプリでは決めない
- 白と黒はマッチごとに偶然で決まる。報告の締め切りとマナーの目安はスマブラSP と同じ

## 既知の限界

次の点は、今の仕組みでは防げていません。

- 鍵を用意すれば、捨てアカウント同士で勝ちを偽装できます。レートの対象になる「紐づけあり」は紐づけの書き方が合っていればよく、その SNS アカウントを本当に持っているかまでは確かめていません。短い間に同じ相手と続けた対戦の重みを下げることと、マッチ条件で軽くしているだけです。
- 同じ X や GitHub のアカウントを、いくつものアカウントに紐づけられます。止めてはおらず、選手の画面と公開 API で並べて見えるようにしているだけです。
- 結果が食い違ったとき、どちらが嘘をついたかは分かりません。双方の回数に数えます。
- X の紐づけは X の埋め込み用の API（oEmbed）で確かめています。X がこの API を止めると、確かめられなくなります。
- 配信される JavaScript がすり替えられると、ページが開いている間は端末の鍵を使われます。鍵そのものは持ち出されず、復活の言葉で復元できますが、取り消すまでの対戦の結果（最大でおよそ1日分）は残ることがあります。
- 同じように、ページを一度開かれただけで、端末の期限（最大90日）までの各日の使い捨ての鍵の証明を、先に作られることがあります。KEL に跡が残らないので気づけません。端末を取り消すか、復活の言葉で入れ替えると、それ以後の日の証明は使えなくなります。
- GitHub Pages では、同じ owner の Pages サイトはすべて origin（`<owner>.github.io`）が同じです。ほかのサイトの JavaScript から端末の鍵を使える状態になります。そのため、このアプリは専用の Organization（`nostr-rating`）で配信しています。fork して公開するときも、独自ドメインか、このアプリ専用のアカウントで配信してください。
- KEL の「先に見た版」を決めるのは、スナップショットを作る人です。誰でも作り直して確かめられますが、ここは中央に寄った部分です。
- 1つの秒に300件より多くのイベントを出したアカウントは、その回の報告と紐づけが使われず、対戦は相手の報告どおりに確定します。その回に初めて紐づけたアカウントの対戦と、記録済みの KEL で確かめられない対戦は、その回は数えません。
- まだ知らないアカウントどうしの対戦は、攻撃を受けているときに取りこぼすことがあります。スナップショットでは、どちらかが既知のアカウントと対戦すれば、以後は取りこぼしません。アプリの締め切り前の暫定の表示では、既知のアカウントの対戦も取りこぼすことがあります。
- `created_at` は本人が決められる値です。締め切りの判定は完全ではありません。
- 公開リレーはイベントを永久には保持しません。古い対戦の検算は、スナップショットとイベント ID 一覧が頼りです。
- アカウントの公開情報（kind 30756）は置き換え可能なイベントです。更新されると古いバージョンが消え、過去のスナップショットを完全には再計算できなくなります。
- `Math.exp`／`Math.log` の結果は、ブラウザによって末尾のビットが違うことがあります。値を小数第6位で丸めて吸収していますが、まれにずれる可能性は残ります。正とする値はスナップショットです。
- 申込者の待ち時間が切れた直後にマッチが届くと、片方だけが成立したと思う対戦が残ることがあります。双方が報告しなければ、どちらにも数えません。
- 一度送った報告は取り消せず、送り直しても有効なまま残ります。押し間違えた報告に相手が合わせると、その内容で確定します。
- 中止の組がそろったあとでも、どちらかが勝ち・負け・引き分けを送ると、その人の中止は数えなくなります。相手が合わせなければ、締め切りで食い違いになります。締め切りのあと、スナップショットができる前に日時を遡らせて送られると、相手は合わせられません。変わるのはマナーの目安の分類だけで、マナーの目安の合計もレートも変わりません。
- 募集や申し込みを大量に出してマッチングを妨げることは、範囲の検査と申し込み件数の上限で軽くしているだけです。
- クライアントは同期のたびに、そのシーズンの選手の部品（1人あたり約0.7KB、gzip で約0.2KB）と、直近2〜3日に動いたアカウントの KEL（1人あたり約1〜2KB）を読みます。どちらも中身が変わる毎日の最初の同期で読み直します。1シーズンの選手が数万人を超えたり、毎日動くアカウントが数千人を超えたりすると、その同期で読む量は圧縮前で数十MB になります。
- スナップショットは GitHub Pages から配ります。Pages には配信量の目安（月100GB）と、サイト全体の上限（1GB）があります。KEL の部品だけで、累計およそ50万アカウントでサイト全体の上限に届きます。
- マッチングでは、待っている人がそれぞれ数秒ごとに全員の募集を読みます。リレーが返す量は待っている人数の2乗で増え、リレーが1回に返す件数の上限を超えると、候補の一部が見えなくなります。

## ローカルで動かす

Node.js 22 以上と Docker が必要です（GitHub Actions では Node.js 24 で動かしています）。

```bash
npm install
npm run relay:up                 # ローカルリレーを ws://localhost:7777 で起動
npm run dev                      # Web アプリ（ローカルリレーに接続）
```

ブラウザで表示された URL を2つの別ウィンドウ（片方はシークレットウィンドウ）で開くと、自分同士で対戦を試せます。

開発サーバーは、スナップショットが無ければ今のシーズンの最初から計算します。手元でスナップショットを作って読ませるときは、次のように書き出します。

```bash
npm run snapshot -- --cutoff "$(date +%s)" --relays ws://localhost:7777
npm run site -- --out .snapshot-parts/site --app-url http://localhost:5173/
```

`npm run snapshot` は、リポジトリの `snapshots/` に目次を書きます。手元で試した目次はコミットしないでください。

### スマホで確かめる

同じ LAN にあるスマホから開くときは、`npm run dev` の代わりに次を使います。

```bash
npm run relay:up
npm run dev:lan                  # https で LAN に公開し、/relay をローカルリレーへ中継する
```

表示される `Network:` の URL（`https://192.168.x.x:5173/` など）をスマホで開きます。

- 端末の鍵（WebCrypto）と記録の保存（OPFS）は https でしか動かないので、自己署名の証明書で配ります。初めて開くと「この接続ではプライバシーが保護されません」などの警告が出るので、詳細から進んでください。
- リレーにはページと同じアドレスの `/relay` を通してつなぎます。スマホから開発機の 7777 番へ直接はつなぎません。
- iPhone の Safari では、自己署名の証明書だとリレーにつながらないことがあります。そのときは [mkcert](https://github.com/FiloSottile/mkcert) で証明書を作って渡し、mkcert の CA（`mkcert -CAROOT` にある `rootCA.pem`）をスマホに入れて信頼させてください。

  ```bash
  mkcert -cert-file lan.pem -key-file lan-key.pem <開発機のIP> localhost
  NR_LAN_CERT=lan.pem NR_LAN_KEY=lan-key.pem npm run dev:lan
  ```

- IP の代わりに開発機のホスト名（`<ホスト名>` や `<ホスト名>.local`）でも開けます。それ以外の名前で開くと、保存したときの画面の自動更新がつながりません。その名前を `NR_LAN_HOSTS=<名前> npm run dev:lan` のように渡してください。
- つながらないときは、開発機のファイアウォールで node への着信を許可してください。

```bash
npm test                         # ユニットテスト
npm run typecheck                # 型検査
npm run e2e                      # 2ブラウザの E2E（ローカルリレーが必要）
npm run snapshot -- --cutoff <UNIX秒> [--game <ゲーム>] [--relays ws://localhost:7777]   # --game を省くと全ゲーム
npm run site -- --out <出力先> --app-url <アプリの URL>   # 選手ページと公開 API
npm run recovery:build           # 復活の道具（apps/recovery/dist/nostr-rating-recovery.html）
npm run recover                  # 復活の道具の CLI 版
```

自分の GitHub アカウントでアプリを公開する手順は、[docs/self-hosting.md](docs/self-hosting.md) にあります。

## リポジトリ構成

| パス | 内容 |
|---|---|
| `packages/core` | UI に依存しない中核ロジック（ゲーム定義、ステージ規則、Glicko-2、イベント、結果確定、マッチング、スナップショット） |
| `apps/web` | Web アプリ（React + Vite） |
| `apps/recovery` | 復活の道具（HTML 1ファイル） |
| `scripts/snapshot` | スナップショット・選手ページと公開 API・復活の CLI |
| `configs/` | リレー一覧、ゲームの一覧と定義 |
| `snapshots/` | レートのスナップショットの目次（ゲームごと。部品はリリースに置く） |
| `relay-server/` | 開発用ローカルリレー（nostr-rs-relay の Docker Compose） |
| `docs/spec.md` | 内部設計仕様書（イベントの形式、計算の決まり、取得・同期・効率化の作り） |
| `docs/adr/` | 設計判断の記録 |
| `docs/self-hosting.md` | 自分でアプリを動かす手順 |
| `docs/api.md` | ほかのサイトからレートを読む公開 API |
